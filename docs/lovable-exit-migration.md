## Goal

Remove Lovable-specific build/runtime dependencies and move the app to a Supabase project owned and administered by Victor Kann. Preserve the current React/TanStack application, GitHub source control, Vercel Preview workflow, existing CRM behavior, and all production infrastructure until the replacement has passed preview tests.

## Audit findings

### Build tooling

- `package.json` includes dev dependency `@lovable.dev/vite-tanstack-config@2.23.1`.
- `vite.config.ts` imports that package. The wrapper currently supplies more than a simple config: TanStack devtools, TanStack Start, React, Tailwind, tsconfig paths, Nitro, environment injection, path aliases, dependency deduplication, error logging and sandbox detection.
- The current Vite config also sets the TanStack Start server entry to `src/server.ts`.
- `package.json` has direct dependencies for React, TanStack Start/Router, Vite, Tailwind and Nitro. These must be retained/reconfigured as appropriate, not removed with the Lovable package.
- `.lovable/project.json` contains Lovable template metadata. It is tooling metadata, not app runtime behavior.
- `bun.lock` must be regenerated by Bun after the config package is replaced. Do not hand-edit the lockfile.

### Backend and auth

- `supabase/config.toml` still targets the Lovable Cloud project ref `qguhydbhcenzphackqnz`. Do not point it at a different project until the replacement Supabase project is created/authorized and verified.
- `src/integrations/supabase/client.ts` uses `VITE_SUPABASE_URL`/ `VITE_SUPABASE_PUBLISHABLE_KEY` in the browser and server-side fallbacks. Its missing-config error mentions Lovable Cloud.
- `src/integrations/supabase/client.server.ts` uses `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`. A service-role key is privileged and must exist only in Vercel server environment variables; never expose it through a `VITE_*` variable or client bundle.
- `src/integrations/supabase/auth-middleware.ts` validates bearer tokens using `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`; its missing-config error also mentions Lovable Cloud.
- `src/integrations/supabase/previewAuthStorage.ts` contains a Lovable-editor session broker that recognizes Lovable/GPT Engineer preview domains and uses postMessage to synchronize sessions. It must be replaced with standard browser storage and an explicit SSR-safe strategy, not blindly deleted without checking auth flows.
- `src/integrations/supabase/types.ts` is generated against the old database schema and must be regenerated from the replacement project after the schema is migrated.
- Existing SQL migrations create `prospects`, `user_roles`, the private `has_role` helper, currency validation, and RLS policies. Apply and verify the baseline migrations on the new project before the new Scoreboard migration.
- The current `prospects` table is a sales CRM schema requiring WhatsApp, country, business type, service interest, challenge, desired outcome and investment range. It is not a suitable table for a simple email-only Scoreboard opt-in. Keep Scoreboard records separate.

### Vercel / current safety state

- Public Supabase client variables are currently configured for Preview only and point to the old Lovable Cloud endpoint.
- Production environment variables and the `main` branch have not been changed.
- The connected Supabase account does not list `qguhydbhcenzphackqnz`; do not assume it is a manageable Supabase project. A replacement project must be explicitly selected/created under the user's own organization.
- A privileged server-side `SUPABASE_SERVICE_ROLE_KEY` has not yet been configured for the replacement project.

## Prepared database migration

The accompanying migration file `supabase/migrations/20261010111000_scoreboard_tables.sql` creates:

- `public.scoreboard_leads`: normalized email, optional name, explicit consent, source/UTM attribution, unique submission id.
- `public.scoreboard_assessments`: ten 0–2 answers, five stage scores, a derived 0–20 total, priority leak and submission linkage.
- Public **insert-only** policies; no public read/update/delete access.
- Admin-only read policies using the existing `private.has_role` helper.
- Database-side checks for answer count/range, score consistency and a priority leak that is one of the highest-scoring stages.

The migration assumes the existing baseline `public.app_role` enum and `private.has_role(uuid, public.app_role)` helper are applied first. It is prepared only; it has **not** been applied to any database. Review before applying to the selected new project.

## Execution order

1. **Choose/authorize the replacement Supabase project.** Confirm the owning organization, project ref, region, database health, and admin/schema-migration access. Do not create a billable project without confirming the organization and cost.
2. **Inventory old data and functions.** With authorized read access, export only data/schema that must be retained. Do not delete or pause the old backend during migration.
3. **Bootstrap the replacement project.** Apply baseline SQL migrations in timestamp order, then inspect applied migration history and RLS/table inventory. Resolve drift before adding the Scoreboard migration.
4. **Replace Lovable Vite wrapper.** Recreate the wrapper's required plugins explicitly and use a Vercel-compatible Nitro output preset. Preserve the custom server entry and run a clean build before committing the replacement.
5. **Remove Lovable session broker.** Replace `brokeredPreviewStorage()` with standard local storage for browser auth plus safe server-side auth behavior. Test sign-in, refresh, logout, server functions and CSRF handling.
6. **Update Supabase config and generated types.** Point `supabase/config.toml` to the replacement project only after it is confirmed; regenerate TypeScript types from that database.
7. **Configure Vercel Preview variables only.** Set `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, and server-only `SUPABASE_SERVICE_ROLE_KEY` for Preview. Keep the service-role key out of browser-exposed variables and logs.
8. **Implement the Scoreboard flow.** Capture consented email before the diagnostic; persist the lead with a client-generated submission id; run the ten-question/five-stage assessment; persist answers and stage scores; show the result, PDF download and “Request a Conversion Leak Review” CTA.
9. **Verify on Preview.** Test build, homepage, mobile layout, opt-in validation, duplicate/retry behavior, all ten answers, 0–20 score, priority leak, persistence, RLS, auth flows and server-side errors. Verify the preview uses the new project.
10. **Cut over only after approval.** Do not merge to `main`, switch production variables, delete the old project or promote the deployment until tests pass and the user approves.
